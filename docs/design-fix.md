# 固定装置与「出了问题？」：设备范围评估 + 诊断与配件（设计稿，2026-10-26）

## 1. 问题：哪些东西算「设备」？会不会太冗杂？
用户列出来的一长串：软装、窗户、排水槽、烟囱、窗帘（布艺 / 百叶 / 电动）、烟雾 / CO 报警器、马桶、花洒、灯泡、圣诞装饰、总水阀、燃气总阀、配电箱、各房间插座、吊扇、门（吱呀响）……

**结论：会冗杂——如果每一个都建一条设备档案。** 一套独栋有 15–25 扇窗、3–4 个马桶、40+ 个插座、10 多扇门，一个一条就是上百条，列表不可读，提醒全是噪音，没人会填。
但它们确实会坏、会修、会买配件，又不能完全不管。所以按「它是什么性质」分四类，各放各的地方，**只有前两类进设备保养**：

| 性质 | 例子 | 放哪里 | 记什么 | 提醒 |
|---|---|---|---|---|
| **设备**：一台一条，有寿命、保修、保养周期 | 炉子、热水器、冰箱、割草机、车 | 房屋 → 设备保养（设备 / 工具 / 车辆） | 品牌型号、安装日期、保修、周期、保养记录 | 保养到期、保修到期、检查待处理 |
| **固定装置**：一类一条，位置和数量写在里面 | 马桶 ×3、门、窗户、吊扇、水龙头 / 花洒、窗帘 / 百叶窗、插座 / GFCI、灭火器、烟雾报警器、排水槽、壁炉烟囱 | 房屋 → 设备保养 → 「固定装置」分组 | 位置与数量（主卫 1 · 客卫 1 · 地下室 1）、每处备注；坏了在这一条下记维修 | 多数不设周期（或一年一查）；默认不提醒 |
| **装备**：只记数量和位置，不保养 | 布艺窗帘、圣诞装饰、床品、梯子、电钻 | 储藏 → 装备（新增子类「窗帘布艺」「节日装饰」） | 数量、位置 | 无 |
| **耗材**：会用完、要补货 | 灯泡、电池、滤网、WD-40、融雪盐 | 储藏 → 库存 → 房屋耗材 | 数量、最低库存、关联设备 | 少货进采购 |

另外两样**不是设备、是信息**：总水阀 / 燃气总阀 / 配电箱 / 回路标签 / 水表电表位置，早已在「房屋资料 → 应急信息与关键位置」，爆水管时家人打开手机就能看；插座不用登记每一个，只记有问题的和 GFCI 在哪。

### 1.1 固定装置怎么做到不冗杂
1. **类型上加 `fixture: true`**（`data/house.js`），`kind` 仍是 `equipment`，表结构不变；列表里单独一组「固定装置」，生成页单独一组、**默认不勾**。
2. **一类一条**：`assets.units jsonb = [{ loc, qty, note }]`（迁移 039）。表单里是「位置与数量」块：每处一行（位置下拉 + 数量 + 备注），「再加一处」。卡片上显示「共 3 处：主卫 1 · 客卫 1 · 地下室 1」。
3. **没有周期就没有提醒**：固定装置多数 `interval` 是 12（一年一查）或空；用户不想要提醒就把周期清掉，它只作为「记维修、问毛病、加配件」的挂靠点。
4. 原有的「门窗」类型改名为「窗户」，新增「门」；排水槽、壁炉 / 烟囱、烟雾报警器本来就有，只是打上 fixture 标记（烟雾报警器保留一台一条也行：它有 10 年寿命）。

### 1.2 要不要和 储藏 → 房屋耗材 / 装备 合并？
**不合并，关联。** 三个空间的「动词」不一样：耗材是**用完要补**（数量递减、进采购），装备是**有几个在哪**（数量不变），设备 / 固定装置是**会坏要修**（有记录、有配件、有人工）。硬合并到储藏，要么给炉子加「最低库存」，要么把马桶的维修记录塞进物品表；合并到设备，装备的几十条床品会把保养列表淹掉。

关联方式（已有的 + 这次补的）：
| 关联 | 方向 | 现状 |
|---|---|---|
| 位置 | 三者共用 | 同一份 `LOCATIONS`（设置 → 存放位置），固定装置的每处位置也从这里选，位置的「用到的物品 / 设备」计数一起算 |
| 耗材 ↔ 设备 | 物品表单「关联设备」`items.asset_ids`；设备类型 → 耗材模板 `ASSET_SUPPLIES` | 已有；这次补 门 → WD-40、吊扇 → LED 灯泡 |
| 装备 → 设备 | 装备物品页「升级为设备」（`#/asset/new?from_item=`） | 已有 |
| 配件 → 库存 → 采购 | 诊断页的每个配件先按名字匹配库存（「家里有：WD-40 · 车库 · 剩 1 罐」），没有才「加入采购」（分类 维修耗材，带估价）；买回来录入购物进房屋耗材 | **这次新增**（§3） |
| 设备 → 采购 | 设备页「相关耗材」→ 加入采购 | 已有 |

## 2. 「出了问题？」要解决什么
用户想要的流程：描述一个毛病（最好能拍照）→ 分析原因 → 给方案 → 方案里要买的东西确认后进购物篮 → 告诉我去哪买、性价比。例子：马桶把手坏了应该换把手不是换马桶；门吱呀响应该上 WD-40 而不是叫人。

沿用 docs/design-ask-y.md 的原则：**先静态、再展开、最后才问 AI**，三层：

```
#/house/fix?asset=<id>                     （设备枢纽里一行「🩺 出了问题？」；设备列表顶部一句；咩咩咩页一个话题）
┌ 哪台设备 / 哪里：[🚽 马桶（共 3 处：主卫 1 · 客卫 1 …）▾]    类型 · 已用 8 年 · 上次保养 2026-03        ┐
│ 怎么了？[主卫马桶冲完一直有细细的水声……]      [📷 拍照 / 选图] ×3                                   │
│ [问咩咩]  [复制提示词]  [换模型]                                                                   │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
┌ 咩咩的诊断                                                                   [复制] [追问]        ┐  ← 第 ② 层：JSON 结构化，不是一段散文
│ 结论：止水皮老化关不严，水箱慢漏后进水阀补水。                                                    │
│ ⚠️ 马上处理（有才显示）                                                                            │
│ 可能原因： [很可能] 止水皮老化 — 怎么确认：滴色素 15 分钟   [可能] 进水阀 …                       │
│ 1. 换止水皮  [自己能做] [简单] ⏱ 约 20 分钟 💲 $6–15                                              │
│    1) 关角阀 2) 冲掉水 3) …                                                                       │
│    要买的配件                                                   [全部加入采购]                    │
│    · 马桶止水皮 flapper · 3 英寸 · 1 个 · ≈ $6–15     ✓ 家里有：… / [加入采购]                   │  ← 第 ③ 层
```

### 2.1 第 ① 层：常见小毛病（离线、零成本）
`data/care.js` 新增 `QUICK_FIXES[type] = [{ s 症状, why, diy[], parts[{ name, q, spec, qty, unit, price }], pro, note }]`。第一版 21 类设备 39 个配件：门（吱呀响：硅基润滑剂 / WD-40，**食用油不建议**——发黏粘灰几周后更响）、马桶（止水皮、进水阀、蜡圈、把手）、水龙头 / 花洒（阀芯、除垢）、吊扇、烟雾报警器、插座 / GFCI、百叶窗、窗户、排水槽、车库门、垃圾处理器、热水器、灭火器、浴室排风扇、洗碗机、洗衣机、烘干机、冰箱、炉子、空调、排水泵。`q` 是五金店网站的英文搜索词。

### 2.2 第 ② 层：问咩咩（结构化 JSON）
- 上下文沿用 `ask.js` 的 `ctx.asset / ctx.vehicle`（类型、年限、上次保养），固定装置再带「位置与数量」；不带备注、人名、地址。
- system 在 `generalPrompt` 基础上加：优先修零件不换整台；配件名要通用可搜；给当地价格区间；燃气 / 电 / 结构要叫人；**只返回 JSON**。
- 返回形状：`{ summary, urgent, replace, causes[{cause, likelihood, check}], fixes[{title, diy, difficulty, mins, steps[], tools[], parts[{name, q, spec, qty, unit, price, where}], cost, note}], pro{when, who, cost} }`。
- `parseFix()` 只接受合法 JSON，逐字段截断（causes ≤ 4、fixes ≤ 3、steps ≤ 8、parts ≤ 6），所有内容转义后只当文字显示。
- 照片最多 3 张，`compressImage(file, 1280)`；模型不能读图时按钮置灰并提示换 Gemini。没 key / 额度用完 → 「复制提示词」。
- 「追问」把问题 + 诊断摘要带到整页咩咩咩；「记到保养记录：待处理」写一条 `inspect / needs_repair`，设备进待处理、首页提醒，直到记维修。

### 2.3 第 ③ 层：配件 → 家里有没有 → 采购 → 在哪买
1. **先查家里**：`findStock(name)` 按名字的词匹配库存（「硅基润滑喷剂」对上「WD-40 润滑防锈剂」），显示在哪、剩多少、少货徽章；有就不默认买（按钮变成「还是买一个」）。
2. **加入采购**：`shopping_list` 一行：名称 = 配件名 · 规格（≤ 60 字），数量、单位，分类 `house_repair`（维修耗材），`amount` 取估价区间下限（预算提示用）；同名未买的不重复加；「全部加入采购」按方案批量加。
3. **在哪买**：按地区给搜索链接，不是比价——模型不联网、浏览器也拿不到各店实时价格。北美：Home Depot / Lowe's / Ace Hardware / Menards / Amazon / Walmart；中国：京东 / 淘宝 / 拼多多。搜索词用配件的英文 `q`（中国用中文名）。页面上明确写「价格是估计、链接只是搜索入口」。
4. 买回来走「录入购物」（拍小票）进 房屋耗材 → 维修耗材，下次同样的毛病就显示「家里有」。

### 2.4 「打通 muse ai」
仓库和设计里都没有叫 muse 的东西，我没查到它指什么，这次没接。如果指某个比价 / 购物助手，接法是：配件行的「在哪买」多一个按钮，把 `name + spec + q` 交给它；需要知道它的入口（网址 / API / App 链接）。

## 3. 不做的
- 不给每个插座 / 每扇窗建档；不做房间平面图。
- 不做实时比价、不抓取商店价格。
- 不自动下单、不加购物车到第三方；只进自家采购清单。
- 常见小毛病的英文翻译第一版未做（English 下回落简体）；AI 诊断按界面语言回答。
