# 收款方 / 付款方 与 统一时间条 设计

> 2026-11-05，草案，待确认后分期实施。相关：[design-finance-ia.md](design-finance-ia.md)（财务信息架构）、[design-income-ledger.md](design-income-ledger.md)（收入口径）、[design-categories.md](design-categories.md)（花费分类、经济性质）。
> 计划迁移：062（收款方汇总 + 改名合并 RPC）。不建新表（别名规则、合并记录存在 `meta`），备份不用改。

## 0. 问题与成功标准

**问题**
1. 花费的「商店」标签名不准：账单、订阅、保险、Zelle 收款人都不是商店；它和收入的「付款方」是一对，却长得完全不一样（一张横条图 + 折叠的表，没有搜索、排序、改名）。在宽屏上「商店」「导出打印」也被塞进「更多」，明明放得下。
2. 财务里有 **4 套各自为政的时间范围**（花费 `state.stats.months`、收入概览 `inc().ov.range`、收支对比 `windowOf`、对账单 / 净资产 / 付款方各自的短列表）：选项不同（近 9 个月只在花费有，近 24 个月 / 去年 / 全部历史只在收支对比有）、口径不同（日历月 vs 滚动天数）、只有收支对比有「周期」和「自定义」。在花费和收入之间切换，时间范围不跟着走。
3. 对账单导入时收款方名 = 描述的前三个词，Amazon 一家就会变成 `AMAZON MKTPL`、`AMAZON COM`、`AMZN MKTP US`…… 好几个收款方，排行被拆散；历史数据没有工具合并。
4. 付款方页顶上只有一句「67 个付款方，收入 xxx，另有资本流入 xxx（不计收入）」，看不出集中度和结构。

**成功标准**
- 花费「收款方」和收入「付款方」用同一套版式：指标卡 → 图表（可点）→ 可排序 / 搜索的表 → 改名 / 合并；宽屏上主标签不进「更多」。
- 财务所有「看一段时间」的页面用同一个时间条组件、同一组选项、同一种口径；花费 ↔ 收入切换时范围不变。
- 导入后 Amazon（除 Prime 会员）只出现一个收款方「Amazon」；历史数据能预览后一键合并，并可撤销。
- 不新增数据表；SQL 只用在「全历史、整张表」的聚合和批量改名上；几十、几百行的结果读一次在内存里排序 / 筛选。

## 1. 花费「商店」→「收款方」

### 1.1 命名
- 标签、标题、表头、空状态里的「商店」统一改成 **收款方**；记账表单里已经是「商店 / 收款方」，保留（照顾线下购物的说法）。
- 筛选里「全部商店 / 收款方」→「全部收款方」；「未填写商店」→「未填写收款方」。数据库列名 `purchases.store` 不改。

### 1.2 导航：「更多」改成按宽度自动收（priority+ 模式）
现在 `SPEND_TABS` 第 5 个元素 `true` = 固定进「更多」，和屏幕宽度无关。改为业界常用的 **priority+ 导航**：
- 所有标签先一字排开；放不下时，从**最后一个**开始收进「更多」，直到放得下（`ResizeObserver` 量 `tabStrip` 的宽度，窗口变化时重算）。
- 标签顺序 = 优先级：花费 `概览 · 明细 · 分类 · 收款方 · 导出打印`；收入同理。第 5 个元素的含义改成「窄屏时优先收起」，不再强制。
- 当前所在的标签永远显示在外面（被收起时显示在「更多」按钮上，现在已有）。
- 手机（< 641px）维持现状：下拉选择。
- 效果：笔记本宽屏上花费 5 个标签全部直接显示；收入标签多，按实际宽度收后面几个。

### 1.3 页面结构（和付款方共用）
```
[ 时间条：时间范围 ▾ ]  （§2，与全财务共享）
┌ 指标卡 ───────────────────────────────────────────────┐
│ 收款方 128 家 │ 花费合计 $9,312 │ 前 5 家占 61% │ 最大：Amazon $2,140 │
└──────────────────────────────────────────────────────┘
┌ 图表（§4）────────────────┐ ┌──────────────────────────┐
│ 前 10 收款方（横条 + 占比） │ │ 按一级分类（环形图）       │
└──────────────────────────┘ └──────────────────────────┘
[ 搜索 ][ 分类 ▾ ][ 性质 ▾ ][ 排序 ▾(手机) ][ 清除筛选 ]   [ 多选合并 ][ 导出 CSV ]
┌ 表：收款方 | 主要分类 | 次数 | 合计 | 占比 | 平均每笔 | 最近一次 | 操作 ┐
│ Amazon      生活购物   46   $2,140  23%   $46.5    11-02     改名 / 合并 │
│ …                                                                    │
└ 每页 pageSize() 条 + 继续加载 ┘
```
- 表头点击排序（和付款方一样，`aria-sort`）；手机用排序下拉。
- **点收款方名称 → 跳到明细并套上这家**（和现在的钻取一致）。
- 「其他商店（N 家）」这一组不再需要：表能翻页、能搜索，前 N 名的合并只留在图里（§4）。
- 账单 / 订阅 / 保险：没填收款方时仍按账单收款方归组（SQL `store_txt` 现有规则不变），表里加一个小标记「账单」。
- 资本性 / 投资：沿用花费页现有的「排除资本性 / 投资」开关口径，指标卡写明「不含转账」。

### 1.4 数据：新 RPC `spend_payees`（迁移 062）
现在的 `spend_rollup_store` 按 月 × 商店 × 分类 × 性质 聚合，算不出「最近一次」的具体日期，前端还要再合并。改为一个按收款方直接汇总的函数：
```
spend_payees(p_household, p_f jsonb) → table(store_key, name, n, sum, last_at, top_cat, cats jsonb, is_bill bool)
```
- `p_f` 和 `spend_filtered` 同一个筛选对象（时间范围、分类、性质、搜索），规则只有一份。
- 行数 = 收款方个数（几百），前端排序 / 翻页 / 搜索都在内存里做。
- `security invoker`，走现有 RLS。

## 2. 统一时间条（评估 + 方案）

### 2.1 评估：哪些页面该用「周期 + 时间范围」

| 页面 | 现状 | 建议 | 理由 |
|---|---|---|---|
| 花费 · 概览 | 范围 | **范围 + 周期**（月 / 季 / 年） | 有走势图；看一年以上时按季 / 年更清楚 |
| 花费 · 分类 | 范围 + 月份 | **范围 + 周期** | 每类的月度走势同上 |
| 花费 · 收款方 | 范围 + 月份 | **只要范围** | 排行榜，没有时间轴；周期没意义 |
| 花费 · 明细 | 年份 + 月份两个下拉 | **范围（独立状态）+ 自定义起止日** | 列表筛选，不该被仪表盘的选择悄悄改掉；钻取进来时套上来源的范围 |
| 花费 · 导出打印 | 3/6/12 | 跟随共享范围 | 打印「我正在看的那段」 |
| 收入 · 收支总览 | 范围 | **范围 + 周期**（双周 / 月 / 季 / 年） | 有 12 个月走势；工资按双周发 |
| 收入 · 类型 | 范围 + 月份 | **范围 + 周期** | 同花费分类 |
| 收入 · 付款方 | 今年 / 近3年 / 近5年 / 全部 | **只要范围** | 同收款方 |
| 收入 · 收支对比 / 导出 | 范围 + 周期 + 自定义 | 保留，改用共享组件 | 已经是目标形态 |
| 预算 · 趋势 | 用花费的范围 | 跟随共享范围；**预算本身固定按月** | 预算的单位就是月，周期不开放 |
| 对账单 · 全部流水 | 自己的短列表 | 范围（独立状态） | 列表筛选，同明细 |
| 净资产 | 近12 / 近24 / 全部 | 范围（只给 ≥ 近 12 个月的选项） | 快照每月一次，短范围没意义 |
| 借贷 · 总览 | 全部历史 | **不加** | 余额是「此刻」的量，不是一段时间的流量 |
| 账单 · 缴费记录 / 医疗 · 年度报表 | 年份下拉 | **不改** | 按税年 / 账单年看，年份下拉最准确 |

结论：**仪表盘类页面统一成「时间范围（必有）+ 周期（有走势图才有）」**；列表类页面用同一组范围选项但各自保存状态；「此刻余额」和「税年报表」保持原样。

### 2.2 统一的选项与口径
```
时间范围：本月 · 上月 · 近 3 个月 · 近 6 个月 · 近 12 个月 · 今年 · 去年 · 往年 ▸(YYYY) · 近 3 年 · 近 5 年 · 全部历史 · 自定义…
周期：    双周（仅收入页）· 月 · 季 · 年
```
- **口径统一为日历月**：「近 3 个月」= 本月 + 前 2 个整月（花费现在就是这样）；收支对比现在的「滚动天数」改成日历月，否则同一个「近 3 个月」在两页数字不同。
- **本月未完**：含本月的范围，「月均」只用已结束的月份算（`fullMonths` 已有），并在指标卡上注明「本月到 11/05」。
- **比上期**：固定长度的范围（本月、近 N 个月、今年至今）和上一段等长时间比；今年至今和**去年同期**比（收入有年终奖、季度分红，比上一段会失真）。全部历史 / 自定义不比。
- 去掉「近 9 个月」「近 24 个月」：用的人少，自定义可以替代。
- **自定义**：仪表盘按**月**选起止（数据是按月聚合的），明细 / 对账单按**日**选起止。
- 周期自动纠正：范围 ≤ 3 个月时不给「年」，范围 > 3 年时默认「季」。

### 2.3 共享状态
- 一个状态 `state.fin.range`（+ `state.fin.unit`），**花费和收入的仪表盘页共用**，存在本机（`localStorage`），切页面不丢。这样「近 12 个月的花费」和「近 12 个月的收入」永远是同一段时间，能直接对照。
- 默认 **近 12 个月**（收入是块状的：奖金、RSU、退税，短窗口容易误读；花费 12 个月也能看出季节性）。
- 「谁的」（成员）只在收入页出现：花费不分人，这一点保持现状并在指标卡下说明。
- 列表页（明细、对账单流水）各自的范围状态，默认「近 3 个月」；从图表钻取进来时套上图表的范围，顶部有标签可以去掉。

### 2.4 实现
- 新模块 `js/core/time-range.js`：选项表、`windowOf(range)`（返回 `{from, to, months[]}`）、`prevWindow`、`labelOf`、`timeBarHtml({unit:true|false, person:true|false})`。从 `income/logic.js` 的 `span*` 抽出来；花费的 `state.stats.months` 和收入的 `inc().ov.range` / `inc().r` 都换成它。
- 旧值迁移：`"3"` → `"3m"`、`"y:2025"` 不变、`"m"` → `"m"`；读到旧值时转换一次。
- 分页面切换，每个页面一个提交，便于回退。

## 3. 收款方名称：导入归一 + 改名 / 合并

### 3.1 导入时归一（`bank-import.js` 的 `merchantName` 之后加一步 `payeeAlias`）
规则按顺序匹配**原始描述**，第一个命中的生效：
1. 用户自己的别名规则（改名 / 合并时自动记下，见 3.3）。
2. 内置规则（`data/payee-alias.js`）：
   - `/amazon\s*prime|prime\s*video|amzn\s*prime|primevideo/i` → **Amazon Prime**（会员 / 订阅，归 `bill_subscription`，现在的分类规则已经这样分）
   - `/amazon|amzn/i` → **Amazon**（`AMAZON.COM*…`、`AMAZON MKTPL*…`、`Amazon.com MKPL*…`、`AMZN Mktp US*…`、`AMAZON RETA*…`、`Amazon Fresh`…）
   - 同样的问题常见于其他大商户，建议一起放进内置表：`Walmart`（WAL-MART / WM SUPERCENTER）、`Costco`（COSTCO WHSE / COSTCO GAS→保留「Costco Gas」）、`Target`（TARGET T-1234）、`Uber` 与 `Uber Eats`、`Apple`（APPLE.COM/BILL）、`Google`、`PayPal *商户名`（取 * 后面的商户名）。
3. 都没命中：现在的 `merchantName` 结果。
- **已学会的分类规则不受影响**：规则按名称存（`_bank_rules`）；`learnedFor` 先查归一后的名字，查不到再用旧的原始键查（兼容旧规则），命中后顺手按新名字补存一条。
- 内置分类规则仍然按原始描述匹配，所以 Prime → 订阅、其余 Amazon → 生活购物 不变。

### 3.2 历史数据批量整理（「整理收款方」）
入口：收款方页工具条「整理收款方」，以及导入完成页的提示（「有 N 个收款方可以按 Amazon 等规则合并」）。
1. 预览：按 3.1 的规则扫描全部花费的收款方（RPC 读去重后的收款方列表 + 笔数，几百行），列出建议：
   `AMAZON MKTPL（31 笔）、AMAZON COM（12）、AMZN MKTP US（3） → Amazon（46 笔，$2,140）`，每组可取消勾选、可改目标名。
2. 确认后一次执行（RPC `rename_payees`，见 3.4），提示「已合并 N 组、M 笔」。
3. **可撤销**：执行结果（每笔的 id 和原收款方）存进 `meta._payee_merge_log`（最近 10 次），「撤销上次整理」一键还原。
- 收款方是导入时顺带写进「名称」的（名称 = 收款方的那些行），名称也一起改；用户自己改过名称的行（名称 ≠ 原收款方）只改收款方。

### 3.3 改名 / 合并按钮（和付款方一样，再加多选）
- 每行「改名 / 合并」：行内表单，输入新名字（带已有收款方联想），提示「和已有的同名收款方会合并成一个」。
- **多选合并**：勾选几行 →「合并为…」→ 默认选笔数最多的那个名字。比一个一个改名快，适合 Amazon 这种 5、6 个变体。
- 每次改名 / 合并都**记一条别名规则**（`meta._payee_alias`：原名键 → 新名），以后导入同样的描述自动用新名——不用再整理第二次。规则可在「银行导入 → 已记住的规则」里查看、删除（和分类规则放一起）。
- 也提供撤销（同 3.2 的日志）。
- 付款方（收入）同步加上「多选合并」和「记住别名」，两边一致。

### 3.4 迁移 062
- `spend_payees(p_household, p_f)`：§1.4。
- `rename_payees(p_household, p_from text[], p_to text)`：`update purchases set store = p_to, name = case when lower(btrim(name)) = lower(btrim(store)) then p_to else name end where household_id = … and lower(btrim(store)) = any(p_from) returning id, 原 store, 原 name`；`security invoker`（走 `purchases_all` RLS），`p_to` 截到 40 字。
  - 账单花费没填收款方、靠账单收款方显示的行：只能在账单上改收款方（提示用户），不在这里改，免得账单和花费不一致。
  - 医疗 / 事件型账单的提供方同理，在那张账单上改。
- 不建新表 → `backup_family` / `TABLES` 不用改。
- 重复检测（`dup-check.js`）按收款方比对：合并后旧数据和新导入的名字一致，查重反而更准。

## 4. 付款方 / 收款方的图表

### 4.1 指标卡（替代顶上那一句话）
| 收入 · 付款方 | 花费 · 收款方 |
|---|---|
| 付款方数 | 收款方数 |
| 认定收入合计（比上期 ±%） | 花费合计，不含转账（比上期 ±%） |
| 资本流入（不计收入），单独一张灰色卡 | 每笔平均 |
| 前 3 家占比（集中度：工资占比高 = 收入依赖单一来源） | 前 5 家占比 |
| 最大付款方 | 最大收款方 |

每张卡可点：合计 → 明细；最大付款方 → 套上这家筛选。

### 4.2 图表（两页同一套组件）
1. **前 10 名横条图**（`Charts.hbars`，已有）：名称 + 金额 + 占比%，其余合成「其他 N 家」。**点条 = 在本页表格筛到这一家**；条旁「明细 ›」才跳页。
   - 横条比饼图更适合排行：名字长、家数多，饼图超过 5~6 块就分不清（可视化通行做法）。
2. **按类型 / 分类的环形图**（`Charts.donut`）：收入按一级类型（工资、投资收益、赠与…），花费按一级分类。超过 6 块合并成「其他」。**点扇区 = 套上类型筛选**（表格和横条图一起变），上方出现可去掉的筛选标签。
3. （第二步）**展开行看走势**：点表格里一行的展开按钮，显示这家近 12 个月的小柱状图 + 分类构成——看出「Amazon 是不是越买越多」「工资哪个月变了」。
- 所有图表元素可键盘操作（`ch-hit`：`role="link"`、`tabindex`）；颜色之外都有文字和数字；深浅色都用 CSS 变量。
- 交互规则统一：**本页有的筛选维度，点了就在本页筛**；要看每一笔，用「明细 ›」。

### 4.3 收入与花费的差异（刻意保留的不同）
| | 收入 · 付款方 | 花费 · 收款方 |
|---|---|---|
| 金额口径 | 认定收入；资本流入单列不计 | 现金流出，不含转账；资本性 / 投资按开关 |
| 成员 | 有「谁的」 | 不分人 |
| 环形图维度 | 收入类型 | 一级分类 |
| 集中度含义 | 收入依赖单一来源的风险 | 钱主要花在哪几家 |
| 周期 | 不需要（排行） | 不需要（排行） |

## 5. 分期

| 期 | 内容 | 迁移 | 价值 |
|---|---|---|---|
| P1 | 导入归一（Amazon 等内置规则 + 旧分类规则兼容）；「商店」→「收款方」命名；priority+ 导航 | 无 | 立刻止血：新导入不再拆散 |
| P2 | `spend_payees` / `rename_payees`；收款方页重做（指标卡、横条、环形、表、改名 / 多选合并、整理收款方 + 撤销、别名规则）；付款方页同一套组件 | 062 | 合并历史数据，两页一致 |
| P3 | `js/core/time-range.js`；逐页换成统一时间条（花费概览 / 分类 → 收入总览 / 类型 → 收支对比 → 预算 / 净资产 / 列表页） | 无 | 一致的时间体验 |
| P4 | 展开行的单家走势；导入完成页的「可合并」提示 | 无 | 锦上添花 |

## 8. 走势图的统一周期（2026-11-06）

问题：时间范围选得长（全部历史、近 5 年），按月的走势图柱子又细又密，看不清；收支对比的并排柱（收入 / 消费 / 其他）更挤。

规则（`js/core/time-range.js`，各页通过 `trendPeriods()`（`js/stats/views.js`）使用）：

1. 一张图最多 24 格（`SLOT_CAP`）。「自动」= 放得下的最细周期：24 个月以内按月，6 年以内按季，再长按年。
2. 一个共享的「周期」下拉（`#finUnit`，存本机 `hmh-fin-unit`），放在时间条里：花费 概览 / 分类、预算趋势、收入 收支总览 / 类型、收支对比（多一个「双周」，最多 12 个月）、净资产走势。
3. 太密的选项在下拉里灰掉并写明「这段时间太长，不可用」；已存的选择放不下时退回自动，图上方提示「按月太密，已改按季」。导出页不限（按月导 5 年也行）。
4. 流量（花费、收入、现金流）按周期求和；余额（净资产快照）取每期最后一个月（`lastByPeriods`），不相加。
5. 不完整的周期（本月 / 本季 / 今年至今，或范围只盖住一部分）画浅色虚边、折线点空心，图下一行说明，数据表里标「（不完整）」。
6. 并排柱子（收支总览的 收入 vs 消费、收支对比）超过 12 期改画折线；净现金流仍是一期一根柱子。
7. 标题跟着周期：「走势 · 按季」；点柱子 / 点到对应那一期的明细（花费按月份列表，收入按日期段）。
8. 固定窗口的小图（医疗近 12 个月、未来 13 周账单、收款方 / 付款方展开的近 12 个月）不变。
